## 1. Web Interface Accessibility (WCAG 2.1 AA)

All web-facing components in this project, including operational dashboards, API documentation portals, and administrative panels, must comply with the Web Content Accessibility Guidelines (WCAG) version 2.1 at the AA conformance level. WCAG 2.1 AA is the internationally recognized standard for digital accessibility and is required by law in many jurisdictions including the European Accessibility Act, Section 508 in the United States, and the Accessibility for Ontarians with Disabilities Act (AODA) in Canada. Compliance is not optional; it is a project requirement that will be validated through automated testing in CI, manual review during design handoff, and periodic third-party audits.

### Perceivable

The Perceivable principle requires that all information and user interface components be presentable to users in ways they can perceive, regardless of their sensory abilities. This means that no information can be presented solely through a single sensory channel. For this project, the Perceivable principle translates into specific technical requirements. All non-text content (icons, charts, status indicators, data visualizations) must have text alternatives that serve an equivalent purpose. Dashboard charts must include data tables as alternatives, accessible via a toggle or disclosed in an accordion section. Live data feeds must provide real-time text descriptions of changing values. Captions must be provided for any multimedia content, including training videos and recorded demos. Content must be adaptable to different presentation formats without losing information or structure, which means dashboards must be usable with custom stylesheets, high contrast modes, and enlarged text. Content must be distinguishable, which means color cannot be the sole indicator of information; patterns, labels, and icons must supplement color coding.

Every dashboard component must be tested against four perceivability criteria. First, text alternatives: every chart must have an associated ARIA label or hidden data table. Second, time-based media: any animated dashboard transitions must have a paused-state alternative. Third, adaptability: the dashboard layout must reflow correctly at 200% zoom without horizontal scrolling. Fourth, distinguishability: all text must meet the 4.5:1 contrast ratio against its background, and all status indicators must use shape or pattern in addition to color.

### Operable

The Operable principle requires that user interface components and navigation be operable by all users, including those who rely on keyboard-only navigation, switch devices, or voice control. Every interactive element in the dashboard must be reachable and operable using keyboard commands alone. Tab order must follow a logical sequence that matches the visual layout, and focus indicators must be clearly visible with a minimum contrast ratio of 3:1 against the background. Users must be given enough time to read and use content; any auto-refreshing data panels must provide a pause button and allow users to control the refresh interval. Content must not flash more than three times per second to avoid triggering seizures in users with photosensitive epilepsy. This is particularly relevant for dashboard animations, real-time data feeds, and status change indicators that might use flashing effects to draw attention. Navigation must be predictable and consistent, with clear wayfinding mechanisms including skip-to-content links, breadcrumb navigation, and consistent heading hierarchy across all pages.

Keyboard accessibility testing must verify that every interactive element (buttons, links, form controls, chart tooltips, dropdown menus) can be activated using Enter or Space, that modal dialogs trap focus correctly, and that focus returns to the triggering element when a dialog closes. The dashboard must provide keyboard shortcuts for common actions (refresh data, toggle filters, switch views) and these shortcuts must be documented in an accessible help panel.

### Understandable

The Understandable principle requires that information and operation of the user interface be understandable to all users. This means that content must be readable and predictable, and that users must receive help when they encounter errors or need assistance. All dashboard text must use plain language, avoiding jargon unless it is defined in an accessible glossary. Abbreviations and acronyms must be expanded on first use or linked to definitions. Form inputs must have associated labels, and error messages must clearly identify the error, explain what went wrong, and suggest how to fix it. For example, an invalid date range filter must not just say "Invalid input" but must specify "End date must be after start date. Please select a date after January 15, 2026." Predictable navigation means that identical functionality behaves the same way across all pages; if a filter panel opens on the left on one page, it must open on the left on all pages.

Input assistance is particularly important for administrative panels where users manage service configurations, API keys, and access policies. These panels must provide inline validation, confirmation dialogs for destructive actions, and undo functionality where feasible. Error prevention must be implemented for submissions that have significant consequences, such as deleting a service configuration or revoking an API key.

### Robust

The Robust principle requires that content be compatible with current and future user agents, including assistive technologies. This means that all web components must use valid HTML5, proper ARIA roles and attributes, and follow the WAI-ARIA Authoring Practices for custom widgets. Dashboard components built with JavaScript frameworks (React, Vue, etc.) must implement the correct ARIA patterns for complex widgets like data grids, tab panels, and tree views. All custom components must be tested with at least two screen readers (NVDA on Windows, VoiceOver on macOS) and two browser combinations. Semantic HTML must be used as the foundation; ARIA attributes supplement but never replace native HTML semantics. For example, a button must be implemented as a `<button>` element rather than a `<div>` with `role="button"`, because native elements provide keyboard interaction, focus management, and accessibility for free.

Automated accessibility testing will be integrated into the CI pipeline using axe-core and pa11y, which will catch approximately 30-40% of accessibility issues. Manual testing with screen readers and keyboard-only navigation will catch the remaining issues. Accessibility audits will be conducted quarterly by a third-party firm specializing in WCAG compliance.

## 2. API Accessibility

API accessibility ensures that the programmatic interfaces of this system are usable by all developers, tools, and automated systems regardless of their technical constraints or preferred workflows. While WCAG focuses on human-facing web interfaces, API accessibility addresses the needs of developer tools, code generators, CI/CD pipelines, and assistive technologies that interact with APIs on behalf of users. The principles of API accessibility are: machine-readability, self-description, error clarity, and discoverability. These principles ensure that APIs can be consumed without requiring human interpretation of prose documentation, that errors provide actionable information, and that service capabilities can be discovered programmatically.

### OpenAPI 3.1 Machine-Readable Specifications

All REST APIs must be documented using OpenAPI 3.1 specifications that are valid, complete, and machine-readable. OpenAPI 3.1 is required (rather than 3.0) because it aligns with JSON Schema draft 2020-12, providing stronger type validation and better support for union types, conditional schemas, and reusable components. Every endpoint must include a description, operation ID, request body schema, response schemas for all status codes, and examples for both requests and responses. The OpenAPI spec must be automatically generated from the codebase (not manually maintained) to prevent drift between documentation and implementation. Buf's `buf generate` tool will produce OpenAPI specs from Protobuf definitions, ensuring that the dual-contract strategy (Protobuf for gRPC, OpenAPI for REST) remains synchronized. The OpenAPI spec must be published to a central API portal accessible at `/api/docs` with an interactive Swagger UI or Redoc renderer that supports keyboard navigation and screen readers.

### Meaningful Error Messages

All API responses must include meaningful error messages that go beyond HTTP status codes. Every error response must conform to RFC 7807 (Problem Details for HTTP APIs), providing a `type` URI that identifies the error category, a `title` that summarizes the error in human-readable form, a `detail` that explains the specific occurrence, and a `status` code. For example, a 404 response for a missing catalog item must not just return `404 Not Found` but must return `{"type": "https://errors.example.com/catalog/item-not-found", "title": "Catalog Item Not Found", "detail": "Item with ID 'SKU-12345' does not exist in the catalog. Verify the SKU and try again.", "status": 404}`. Error messages must include remediation hints that guide the API consumer toward resolution, such as suggesting valid parameter ranges, linking to relevant documentation, or indicating which field caused the validation failure. Error messages must never expose internal implementation details, stack traces, or database queries.

### Structured API Documentation

API documentation must be available in structured, machine-parseable formats in addition to human-readable prose. The primary documentation format is the OpenAPI specification itself, which serves as both the contract and the documentation. Supplementary documentation must be provided in Markdown format with structured headings, code examples in multiple languages (Go, Rust, Python, TypeScript), and step-by-step tutorials for common workflows. All documentation must be version-controlled alongside the code it describes, ensuring that documentation updates are part of the same pull request as code changes. Documentation must include request and response examples for every endpoint, error scenario walkthroughs, and authentication flow diagrams. Architecture Decision Records (ADRs) must document the rationale for API design choices, making it accessible for future developers to understand why certain decisions were made.

### gRPC Reflection and Service Discovery

gRPC reflection must be enabled on all gRPC services to support runtime service discovery and dynamic client tools. gRPC reflection allows tools like `grpcurl`, `grpcui`, and Postman to discover service definitions, methods, and message types without requiring pre-compiled client stubs. This is an accessibility feature for developers because it eliminates the need to locate and compile proto files before interacting with a service. Reflection must be enabled in all environments (development, staging, production) with appropriate authentication. Additionally, gRPC health checking must be implemented according to the standard health checking protocol, allowing load balancers and service mesh proxies to detect service availability without making application-level requests.

### Proto Descriptors for Client Generation

Compiled Protocol Buffer descriptors (FileDescriptorSet) must be published alongside each service release, enabling clients to generate type-safe stubs in any supported language without cloning the source repository. This is particularly important for the polyglot architecture of this project, where services are written in Go, Rust, Python, and TypeScript. Each service must publish its compiled descriptors to a central Schema Registry, and the CI/CD pipeline must validate that the published descriptors match the source proto files. Client generation templates must be provided for all supported languages, including build system integration (Go modules, Cargo crates, Python packages, npm packages). The Schema Registry API must provide endpoints for downloading descriptors by service name, version, and package path, enabling fully automated client generation in downstream projects.

## 3. Documentation Accessibility

Documentation accessibility ensures that all project documentation, including architecture diagrams, design specifications, operational runbooks, and API references, is usable by all team members regardless of visual ability, cognitive style, or assistive technology dependency. Documentation is a critical part of the system's accessibility surface area because it is the primary way that developers, operators, and stakeholders understand the system. Inaccessible documentation creates knowledge silos, onboarding barriers, and operational risks.

### Text Alternatives for Architecture Diagrams

All architecture diagrams must include text alternatives that convey the same information as the visual representation. This requirement applies to system context diagrams, service interaction diagrams, deployment topology diagrams, data flow diagrams, and sequence diagrams. The text alternative must be provided in two forms: the Mermaid source code (which is itself a text-based diagram format) and a prose description that explains the diagram's content, relationships, and key takeaways. For example, a service interaction diagram showing the Order service calling the Payment service via the Gateway must include a Mermaid source block and a paragraph stating "The Order service initiates a payment request through the API Gateway, which routes the request to the Payment service. The Payment service processes the payment with the external gateway and returns the result through the Gateway to the Order service. If the external gateway is unavailable, the circuit breaker opens and the Payment service returns a queued-for-retry response."

Mermaid diagrams are preferred over image-based diagrams because they are version-controllable, render consistently across devices, and can be processed by screen readers when the source is included as a code block. All Mermaid diagrams must be validated in CI using the Mermaid CLI to ensure they render correctly. Image-based diagrams are permitted only when Mermaid cannot express the required visual complexity (such as network topology maps), and even then must include a detailed text alternative in the surrounding prose.

### Color as Non-Sole Indicator

Color must never be the sole indicator of information in any documentation, diagram, or dashboard. This principle is derived directly from WCAG Success Criterion 1.4.1 (Use of Color) and applies equally to technical documentation and user-facing interfaces. In architecture diagrams, different service types must be distinguished by shape, pattern, and label in addition to color. In status indicators, states must be distinguished by icon, text label, and pattern in addition to color (for example, "healthy" uses a green circle with a checkmark icon and the text "OK", while "unhealthy" uses a red circle with an X icon and the text "DOWN"). In data charts, data series must be distinguished by line style (solid, dashed, dotted), marker shape (circle, square, triangle), and label in addition to color.

The color palette for all documentation and dashboards must be tested against three forms of color vision deficiency: protanopia (red-blind), deuteranopia (green-blind), and tritanopia (blue-blind). Tools like Sim Daltonism or the Coblis Color Blindness Simulator must be used to verify that all information remains distinguishable when viewed under these conditions. The project's design system must include a color accessibility section that documents the approved palette, the contrast ratios for all text-background combinations, and the supplementary indicators required for each color-coded element.

### Screen-Reader Compatibility

All documentation must be structured for screen-reader compatibility. This means using proper heading hierarchy (H1 for document title, H2 for major sections, H3 for subsections, never skipping levels), providing alt text for all images, using semantic HTML for web-hosted documentation, and ensuring that tables include proper header rows and scope attributes. Long documents must include a table of contents with anchor links, allowing screen-reader users to navigate directly to sections of interest. Code blocks must be formatted with syntax highlighting that uses semantic markup (not just visual coloring) so that screen readers can distinguish code from prose. Lists must be properly nested using `<ul>` and `<ol>` elements, not simulated with dashes or numbers in plain text.

Documentation published as web pages must pass WCAG 2.1 AA automated checks using axe-core. Documentation published as Markdown files must be validated for heading hierarchy, alt text presence, and link accessibility using custom linters integrated into the CI pipeline. PDF documentation must include tagged PDF structures, bookmarks, and reading order metadata to ensure compatibility with screen readers like JAWS and NVDA.

### Minimum Contrast Ratios

All text in documentation and dashboards must meet the minimum contrast ratios defined by WCAG Success Criterion 1.4.3 (Contrast Minimum). Normal text (font size less than 18pt or 14pt bold) must have a contrast ratio of at least 4.5:1 against its background. Large text (font size 18pt or larger, or 14pt bold or larger) must have a contrast ratio of at least 3:1. User interface components and graphical objects must have a contrast ratio of at least 3:1 against adjacent colors. These ratios are minimums; the project design system should target 7:1 for body text (WCAG AAA) where feasible. Contrast ratio validation must be performed as part of the design review process using tools like the WebAIM Contrast Checker or Stark, and automated checks must be integrated into the CI pipeline for web-hosted documentation. Any contrast ratio failure is a blocking CI issue that must be resolved before merge.

## 4. Developer Experience Accessibility

Developer experience accessibility ensures that all developers, regardless of experience level, cognitive style, or disability, can effectively use the project's tools, templates, and documentation to build, test, and deploy services. This goes beyond traditional accessibility to encompass the cognitive accessibility of the development workflow itself. A developer who cannot understand an error message, navigate a CLI tool, or find relevant documentation is effectively excluded from contributing to the project, which undermines the project's goal of reducing cognitive load and enabling efficient polyglot development.

### CLI Tool Accessibility (`--help` and `--json` Output)

All CLI tools in the project must support `--help` flags that produce comprehensive, well-formatted help text and `--json` flags that produce machine-parseable output. The `--help` output must include a description of the tool's purpose, a list of all available commands and flags with descriptions, usage examples for common workflows, and a reference to the full documentation URL. Help text must use consistent formatting across all tools: command names in bold, flags in monospace, examples in indented code blocks. The `--json` output must produce valid JSON with a consistent schema across all tools, including a `status` field (success or error), a `data` field containing the result, and an `errors` field containing any error details. This dual-output approach ensures that CLI tools are accessible both to humans (who read the help text) and to automation systems (which parse the JSON output for CI/CD pipelines, monitoring dashboards, and reporting tools).

CLI tools must also support `--quiet` mode for suppressing non-essential output, `--verbose` mode for detailed debugging output, and `--no-color` mode for disabling ANSI color codes that interfere with screen readers and log aggregation systems. Exit codes must follow the BSD convention: 0 for success, 1 for general errors, 2 for command-line usage errors. This convention makes CLI tools programmable and predictable, which is an accessibility feature for developers who build automation on top of the tooling.

### Error Messages with Remediation Steps

Every error message produced by CLI tools, build scripts, linters, and test runners must include a clear description of what went wrong and specific remediation steps that the developer can follow to fix the issue. Error messages must never simply state "Error" or "Failed" without context. For example, a schema validation error must not say "Schema validation failed" but must say "Schema validation failed: field 'order.items' is required but was not provided. Add an 'items' array with at least one element to the order payload. See https://docs.example.com/schemas/order for the complete schema definition." Error messages must include the file path, line number, and field name where the error occurred, making it possible to jump directly to the problem in the editor.

For build and deployment errors, the remediation steps must include the exact command to run to fix the issue when possible. For example, "Protobuf compilation failed: out-of-date generated stubs. Run `buf generate` to regenerate." This approach reduces the cognitive load on developers, particularly those who are new to the project or unfamiliar with the specific toolchain. Error message quality will be reviewed as part of the code review process, and linters will flag error messages that lack remediation steps.

### Service Scaffolding Templates with Accessibility Comments

Service scaffolding templates (used by the `gstack scaffold` or similar tooling) must include inline comments that document accessibility requirements relevant to the generated code. For example, a React component template must include comments reminding developers to add ARIA labels, implement keyboard navigation, and test with screen readers. A gRPC service template must include comments reminding developers to add meaningful error messages, implement health checking, and enable reflection. A database migration template must include comments reminding developers to consider the impact of schema changes on downstream consumers and to update the Schema Registry accordingly.

These comments serve as guardrails that keep accessibility top-of-mind during development, rather than treating it as an afterthought to be addressed during review. The scaffolding templates must also include placeholder accessibility test files: an axe-core test for web components, a gRPC reflection test for services, and a documentation accessibility check for README files. These placeholder tests fail by default with a message instructing the developer to implement the actual accessibility checks, ensuring that accessibility is tested from the first commit.

### Onboarding Documentation Assuming Zero Context

All onboarding documentation must be written assuming the reader has zero prior context about the project, its architecture, or its tooling. This means that every concept must be defined before it is used, every prerequisite must be listed explicitly, and every step must include the exact commands to run with expected output shown. Onboarding documentation must be validated by having a team member who has never seen the project follow the instructions on a clean machine, and any step that requires clarification or external knowledge must be rewritten until it is self-contained.

The onboarding documentation must include the following sections in order: (1) Prerequisites with exact version numbers and installation commands for each platform, (2) Repository cloning and environment setup with expected output for each command, (3) Build and test execution with expected output and common troubleshooting steps, (4) Architecture overview with Mermaid diagrams and text alternatives, (5) Service-by-service walkthrough explaining each service's purpose, dependencies, and how to run it locally, (6) Development workflow including branching strategy, commit conventions, and PR process, and (7) Getting help with links to chat channels, documentation portal, and escalation contacts. Each section must be independently accessible, allowing a developer to jump directly to the section they need without reading the preceding sections. This structure supports both linear onboarding (new team members reading end-to-end) and nonlinear onboarding (experienced developers looking up a specific procedure).
